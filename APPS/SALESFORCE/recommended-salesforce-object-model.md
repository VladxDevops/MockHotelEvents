# Recommended Salesforce Object Model

## Purpose
This model keeps Salesforce aligned to the mock hotel wedding planning workflow without turning Salesforce into the operational source of truth for venue inventory or final booking execution.

## Standard objects

### Lead
Represents the initial wedding inquiry or prospect.

Recommended fields:
- FirstName
- LastName
- Email
- Phone
- Company
- LeadSource
- Status
- EventType
- PreferredEventDate
- AlternateEventDate
- EstimatedGuestCount
- BudgetRange
- Notes
- CreatedDate

### Contact
Represents the couple, planner, or primary decision-maker.

Recommended fields:
- FirstName
- LastName
- Email
- Phone
- RelationshipType
- AccountId

### Account
Represents the customer or organizing party.

Recommended fields:
- Name
- BillingStreet
- BillingCity
- BillingState
- BillingPostalCode
- BillingCountry
- CustomerCategory

### Opportunity
Represents the sales opportunity for the event.

Recommended fields:
- Name
- AccountId
- PrimaryContactId
- Amount
- StageName
- CloseDate
- EventType
- WeddingDate
- EstimatedGuestCount
- Probability
- OwnerId
- CurrencyIsoCode

## Relationship model
- One Lead can generate one or more Event_Request__c records.
- One Event_Request__c should map to one Opportunity.
- One Event_Request__c may have multiple Venue_Availability__c records.
- One Event_Request__c may have multiple Event_Quote__c records over time.
- One Opportunity can be linked to a single confirmed Event_Booking__c.

## Lifecycle stage mapping
Use clear status values to reflect progress:

- Lead: New, Qualified, Nurturing, Converted, Closed Lost
- Event_Request__c: New, Submitted, Availability Checked, Quote Ready, Quote Approved, Booked, Cancelled
- Event_Quote__c: Draft, Sent, Accepted, Rejected, Expired
- Event_Booking__c: Draft, Pending Approval, Confirmed, Cancelled, Completed

## Integration-friendly guidance
- Salesforce should own customer and sales records.
- Operational systems should own actual venue and booking execution details.
- Add `External_Request_Id__c` and `External_Booking_Id__c` fields for integration traceability.
- Keep correlation IDs and timestamps in the payload so downstream systems can match step-by-step progress.
- Use status fields consistently for both API-driven updates and UI display.

## Recommended implementation pattern for this repo
For the mock project, keep this simplified but realistic:

- Lead captures the wedding inquiry.
- Event_Request__c stores the detailed event requirements.
- Opportunity creates the sales context for the event.
- Venue_Availability__c records external validation results.
- Event_Quote__c holds the generated price proposal.
- Event_Booking__c represents the final accepted event.

## Recommended first version
If you want the smallest useful Salesforce design, start with these objects only:
- Lead
- Opportunity
- Event_Request__c
- Event_Quote__c
- Event_Booking__c

That gives enough realism for a wedding inquiry demo without overengineering the model.
